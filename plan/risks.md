# Risks and guardrails

Each risk names the measurement or check that retires it and the phase item that does it. Fill in
the "Measured" column as results come in.

| # | Risk | What we know | Guardrail | Measured |
|---|---|---|---|---|
| R-1 | Memory and fps on low-end Android | Hermes, V8, LiveKit and Godot in one process. Measured so far: 11–15 fps on the debug template, 14–18 on release, not yet compared with the Godot-exported app from the same commit. | Measure a release build on the Moto Edge 60 Pro and an iPhone before committing the backpack to live 3D (2.9). Budget: no worse than the Godot-exported app on fps, +100 MB RSS at most. Re-checked on the RC in 6.5. | |
| R-2 | Two render surfaces | The transparent backpack surface needed a Mali workaround and is unwired on iOS (`set_surface_on_top` has no iOS equivalent). | Keep the backpack as the single transparent case (D-11); write the iOS surface-order flip in 3.4; the host, not JS, flips it on `avatar_preview_mode`. | |
| R-3 | Soft keyboard for scene text inputs | The engine surface must receive IME focus while RN sits on top; no scene `UiInput` has been tried in the RN host yet. | 2.8 verifies with a test scene on both platforms; the virtual-keyboard height reaches the core (4.14). | |
| R-4 | Two crash handlers | sentry-godot and the Sentry RN SDK both install native handlers. | Decided (D-16): the RN SDK owns native, Rust and engine errors go through the core; 3.9 applies it. | |
| R-5 | Two cores in one process | A separate FFI library would statically link `dcl_core` twice: two runtimes, two sessions, silent. | D-6; a debug assertion counts `Core::install` calls (3.4 exit criterion). On Android confirm `System.loadLibrary("dclgodot")` returns the handle Godot opened. | |
| R-6 | Store update loses the user's session or cache | The 2.0.0 release updates `org.decentraland.godotexplorer`; today's users have `settings.cfg`, `thirdweb_session.json`, `device_anchor.txt`, `attest_session.json` and `content/` under Godot's `user://`. | The core's data dir is that same path on both platforms (D-19) and 1.4 / 3.5 / 4.5 import the old files once. The upgrade test (6.3) updates a device from the store build to the RC and checks the session survives. | |
| R-7 | Unsymbolicated crashes after dropping sentry-godot | Android symbolication only works since the `--build-id=sha1` fix in the engine fork and in xtask's Android RUSTFLAGS; the CI symbol upload targets sentry-godot's project today. | 3.9 keeps the upload for `libdclgodot.so` / dSYM and the engine library against the same Sentry project; a deliberate test crash from Rust and from a scene on both platforms must show symbolicated frames before sentry-godot is removed (repeated on the RC in 6.5). | |
| R-8 | **One developer to the gate, the whole migration** | Phases 1–5 are one person plus AI sessions until 30 Nov, now including the ~14k-line engine-side port. They have no time estimate, so slippage shows only as open items and as `.gd` files still in the tree. | The parity checklist (4.16) and the `.gd` file count are tracked weekly and kept moving incrementally, not at the end. Inside phase 5 the avatar and player go first, because Idle and World need them. If the gate is late, phase 7 shrinks before phase 6 does, and December validation starts on what is already ported. | |
| R-9 | Long divergence from `main` | `main` keeps shipping 1.16/1.17 fixes in GDScript for LMT3; the branch deletes GDScript. | A scheduled automated job merges `main` into the branch daily until the December merge, skipping UI-only changes; deleted-file conflicts resolve as deleted and a fix that matters is redone in RN or Rust (D-31). Phase 1 and 2 PRs are small and reviewable. | |
| R-10 | The team arrives cold | Nobody but Mateo has touched the core, the FFI or the Rust root before December. | Phase-1–4 PRs are written to be read (one module or domain each); 6.0 is an onboarding week where every engineer ships one call end to end before touching phase 7. | |
| R-11 | Engine iteration speed | Rust engine code compiles in minutes and has no live reload. | Accepted. UI iteration moves to RN fast refresh; the emulator shortens the scene loop; `--preview` keeps scene hot reload for creators (5.6). | |
| R-12 | Engine cannot restart in-process | Start once, live until the app dies. | Design driver (D-12): the core holds everything that must survive leaving a world; `exit_world` is tested in 3.2 with enter → exit → enter. | |
| R-13 | The Expo Go workflow ends | A custom TurboModule cannot load in Expo Go. | Accepted (D-21); the no-engine native builds with the mock core replace it; documented in `rn/README.md` with 3.8. | |
| R-14 | Signed-account paths never exercised in the RN app | Friends actions, notifications with data, account deletion, votes and reminders were only recollected, not verified. | The parity checklist (4.16) runs with a signed-in account on both phones; 6.2 repeats it on the device matrix. | |
| R-15 | Native plugin code called from the host | For 2.0.0 the host calls today's Kotlin/Swift plugin code for wallets, push, StoreKit, share and calendar (D-21, D-25) instead of RN libraries. That code was written to be driven by Godot. | Each call is exercised in the parity checklist on a real device; the replacement by RN libraries is item 8.2 after the release, not a 2.0.0 risk. | |
| R-16 | Feature specs arrive late | Phase 7 needs Figma, endpoints and metrics for five features before the gate (D-34). | Without a spec at the gate the feature moves out of 2.0.0 rather than into December's validation work; the core calls for the specified ones are in the FFI before phase 7 starts. | |
| R-17 | **AI-ported engine code changes behaviour** | The whole engine-side port (player, avatar, SDK components, fetcher) is done by AI before 30 Nov; its GDScript tests are ported by subject (D-20). | `--itest` and `--stest` on every PR and the scene-test snapshots in `tests/` must not change after any port. December starts with 6.1 (what the AI got wrong), a device-matrix run and a Genesis Plaza fps and memory comparison against the baseline; QA scripts per domain are executed by someone other than the author. | |
